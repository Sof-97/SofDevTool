# Sortable identifier facts: ULID and KSUID

Researched 2026-08-21 from the canonical ULID specification and implementation, plus the KSUID reference implementation.

## ULID

- **Form:** a ULID is 128 bits / 16 bytes in network byte order: a 48-bit Unix timestamp in milliseconds followed by 80 random bits. Its canonical text is 26 characters: 10 timestamp characters and 16 randomness characters using the uppercase Crockford Base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. Text is case-insensitive and URL-safe; canonical output should be uppercase. [Canonical specification](https://github.com/ulid/spec#specification)
- **Generation:** ordinary generation draws the 80-bit suffix from a cryptographically secure source where possible. The canonical JavaScript implementation uses browser `crypto.getRandomValues` or Node `crypto.randomBytes`, fails if it cannot find a reliable PRNG, and separately exposes ordinary and monotonic factories. [ULID implementation](https://github.com/ulid/javascript/blob/master/source/ulid.ts)
- **Validation and normalization:** accept exactly 26 case-insensitive characters from the ULID alphabet, normalize valid text to uppercase, and reject values above `7ZZZZZZZZZZZZZZZZZZZZZZZZZ`. That upper-bound check matters because 26 Base32 characters can encode 130 bits while ULID has only 128; the specification explicitly requires overflow rejection. The canonical JavaScript `isValid` currently checks length/alphabet but not that upper bound, so the Utility should enforce the specification rather than copy that helper alone. [Overflow rule](https://github.com/ulid/spec#overflow-errors-when-parsing-base32-strings), [current `isValid`](https://github.com/ulid/javascript/blob/master/source/ulid.ts#L121-L136)
- **Inspection:** timestamp extraction is deterministic from the first ten characters and returns Unix epoch milliseconds; the reference implementation exposes `decodeTime`. Displaying ISO 8601 plus the raw millisecond value is appropriate. [Timestamp API](https://github.com/ulid/javascript#ulid-time)
- **Sorting:** fixed-length canonical ULID text sorts by timestamp under ordinary ASCII lexical ordering, and the big-endian binary representation does likewise. Different milliseconds therefore sort chronologically, subject to the accuracy/order of wall clocks. For independently random ULIDs within one millisecond, generation order is not guaranteed. [Sorting and layout](https://github.com/ulid/spec#sorting)
- **Same-millisecond monotonicity:** the specified monotonic algorithm seeds the random suffix once and increments it with carry for each subsequent ID in the same millisecond, producing strict local lexical order; it fails if the 80-bit suffix overflows. The canonical JavaScript monotonic factory also preserves ordering when its observed clock moves backward by retaining the last timestamp. This state is process/factory-local, not coordination across machines or independent generators. [Monotonic specification](https://github.com/ulid/spec#monotonicity), [canonical factory](https://github.com/ulid/javascript/blob/master/source/ulid.ts#L138-L160)
- **Collision/security boundary:** ordinary ULIDs have 80 random bits per millisecond, so uniqueness is probabilistic and collision risk concentrates among IDs sharing a millisecond. A monotonic sequence removes duplicates within one generator until overflow, but independent generators remain uncoordinated. Require a CSPRNG, expose the embedded timestamp as non-secret metadata, and do not describe a ULID as an authorization secret or a mathematical guarantee of uniqueness. [Randomness requirement](https://github.com/ulid/spec#components)

## KSUID

- **Form:** a KSUID is 20 bytes: a big-endian 32-bit unsigned timestamp followed by a 16-byte random payload. The timestamp counts seconds from the custom epoch Unix `1400000000` (2014-05-13 16:53:20 UTC). Canonical text is exactly 27 characters, a fixed-width, delimiter-free, case-sensitive Base62 encoding of the whole 160-bit value. [Reference README](https://github.com/segmentio/ksuid#how-do-ksuids-work), [reference constants/layout](https://github.com/segmentio/ksuid/blob/master/ksuid.go#L14-L40)
- **Generation:** the reference implementation's ordinary generator reads all 128 payload bits from Go's `crypto/rand`; generation for a supplied time and construction from a supplied 16-byte payload are also available. [Reference generation](https://github.com/segmentio/ksuid/blob/master/ksuid.go#L198-L245)
- **Validation and normalization:** require exactly 27 Base62 characters and a decoded value between the reference minimum `000000000000000000000000000` and maximum `aWgEPTl1tmebfsQzFP4bxwgy80V`. Unlike ULID, case changes alter the Base62 value, so no upper/lowercase normalization is valid; canonicalization is parse then re-encode unchanged in meaning. A 20-byte binary form can also be validated directly. [Reference parser and bounds](https://github.com/segmentio/ksuid/blob/master/ksuid.go#L28-L48), [parse implementation](https://github.com/segmentio/ksuid/blob/master/ksuid.go#L164-L178)
- **Inspection:** the reference API exposes both the raw epoch-relative `uint32` timestamp and the corrected UTC time, plus the 16-byte payload. Timestamp precision is one second. [Reference accessors](https://github.com/segmentio/ksuid/blob/master/ksuid.go#L61-L74)
- **Sorting:** both 20-byte binary values and fixed-width Base62 strings sort by the timestamp first. This is only *loose* generation-time ordering: wall clocks can be wrong or move backward, and independently generated KSUIDs in the same second are ordered by random payload rather than creation order. [Reference sorting guarantee and caveat](https://github.com/segmentio/ksuid#1-naturally-ordered-by-generation-time)
- **Same-second monotonicity:** ordinary `New`/`NewRandom` generation is not monotonic inside a second. The reference library has a separate `Sequence` seeded by one KSUID; it keeps the leading 18 bytes and places an increasing 16-bit sequence number in the last two bytes, yielding at most 65,536 ordered IDs. It is not concurrency-safe, does not advance the timestamp, and is better presented as an explicit batch/sequence mode than as KSUID's default guarantee. [Reference `Sequence`](https://github.com/segmentio/ksuid/blob/master/sequence.go)
- **Collision/security boundary:** ordinary KSUIDs have 128 random payload bits per second, making collisions probabilistic but practically remote with a CSPRNG. The reference library warns that its optional faster PRNG can make IDs more predictable and should not be used when security depends on uniqueness. SofDevTool should always use the system CSPRNG, expose the timestamp, and avoid absolute “collision-free” or secret-token claims. [Reference randomness guidance](https://github.com/segmentio/ksuid#high-performance)

## Product recommendation

ULID and KSUID plausibly belong beside UUID generation because all three share the user's core jobs: generate one or many identifiers, validate pasted identifiers, normalize when the format permits it, copy results, and inspect embedded type/time information. They should **not** be presented as UUID versions.

Rename the Utility from **UUID** to **Identifier Generator** (or **Identifiers**) and make the top-level format selector explicit:

- **UUID:** versions 1, 3, 4, 5, 6, and 7, with UUID-specific namespace/name/version controls.
- **ULID:** random or monotonic generation; canonical uppercase output; millisecond timestamp inspection.
- **KSUID:** random generation, with optional explicit ordered-sequence batch mode; case-sensitive output; second timestamp inspection.

Keep v4 UUID as the ordinary random default and v7 as the recommended standard sortable choice. Label ULID and KSUID as interoperable ecosystem formats rather than RFC UUIDs. The shared Utility is coherent if format-specific controls appear only after a format is chosen; cramming them into one flat “version” menu would blur incompatible semantics.
